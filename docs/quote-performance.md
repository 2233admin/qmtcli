# 行情接入性能回放：2026-11-01

[K] 已比较 Rust release、Python 3.15.2 原生协议和 Python 3.11.16 官方
SDK 三条现有实现路径。启动开销差异明显；常驻小请求没有稳定胜者；批量行情加
JSON 输出在这轮回放中 Rust 耗时更低。**这不是实际 QMT、柜台或交易所延迟测试。**
当时大 QMT 未启动外部 XtQuant 行情服务，无法完成真实服务上的同条件比较。

## 测量结果

单位 ms；括号内为五组结果的最小–最大值。常驻项目报告“五组各自每次操作
平均耗时”的中位数，不是单次请求 p50。启动项目为五次新进程耗时的中位数。

|---|---:|---:|---:|

| 常驻连接，2 条查询 | 0.141 (0.101–0.216) | 0.174 (0.095–0.187) | 0.148 (0.145–0.174) |

| 常驻连接，1000 条查询 | 11.95 (11.41–16.52) | 15.76 (15.36–16.42) | 26.96 (26.93–27.22) |

[C] 批量查询加 JSON 的中位耗时，Rust 比本次原生 Python 路径少约 21%，
比本次 SDK 路径少约 51%。这仅描述当前版本、参数和测试适配器，不能据此认定
Rust 普遍更快，或据此替换正式后端。小查询差异小于或接近组间波动，不宣布胜者。
不同场景分别测量，小场景“加 JSON”比另一个场景“仅查询”更快也属于波动。

## 方法与正确性

- 使用自有 `127.0.0.1` 临时端口回放端。返回相同的合成 18 字段行情，含
  Int64 时间戳和五档数组；无真实账户、行情、报单、撤单或共享进程修改。
- 2 条响应帧 427 B，解压 BSON 1023 B；1000 条帧 85,721 B，BSON 490,043 B。
  服务端预生成内容、逐请求更新序列号；客户端每次实际发请求并解码，不缓存结果。
- 每场景五组，轮换执行顺序；每组预热三次。2 条每组计时 300 次，1000 条
  每组 30 次。单客户端顺序请求；未测并发、吞吐上限、长尾、长时间稳定性。
- 计时包含读取、解码、结果条数校验及首条的字段数、时间戳、深度长度校验。
  JSON 场景实际构造完整 UTF-8 输出并计数，但不把完整数据写给 agent。
  校验不是对每个字段逐值对账；不能代替真实服务的语义验收。
- Rust 用实际 `QuoteSession`，Python 原生用实际保留的 `QuoteConnection`，SDK
  用实际 `xtdata.reconnect/get_full_tick`。正式 Python CLI 的每次调用封装不在
  此保留连接计时路径内。Rust 还做返回代码校验，内部有 BSON 所有权复制；版本、
  编解码器和检查并非完全相同，所以不是纯语言性能实验。
- SDK 输出 JSON 382,123 B，另两者 403,123 B：SDK 对整数值浮点数省略 `.0`。
  合成数据的数值含义相同，JSON 字节不同，序列化工作量并非逐字节等量。
- 解码组件也有边界差异：Rust 读完整帧并检查 CRC，Python 从已读帧的 body 解码。
  组件数据用于定位成本，不作为完全等量的编解码器排名。
- 启动使用现有 hyperfine 1.20.0，直接执行、不经 shell；五轮交错，每次验证退出
  成功和服务端恰好多一次查询。文件系统已热，进程新建，含连接认证与一次小查询，
  不是完整 `qmtcli` 命令或 agent 的端到端耗时。

[K] 服务端收到 **10,115 次查询、0 次请求错误**：9900 次计时网络查询、180 次
预热、20 次独立剖析和 15 次启动查询。另有 3300 次计时解码操作不联网。
各批次核对服务端查询增量；18 次连接及认证，SDK 另有 6 次 getDataDir。
所有自有工作进程正常退出。12 次关闭和 6 次空闲连接重置单独计数。
独立负控确认半包头、半包体、坏 CRC 三种输入均被记为错误，正常空闲关闭不记错误。

初轮把 SDK 正常退出时的重置误记为请求错误，原始失败回执保留；修正分类后又
移除基准适配器的提前 profiler 导入，重新全量测量。上表仅取最后一轮。

## 限制、瓶颈与下一步

[K] 主机 32 逻辑核、约 93.7 GiB 内存，开测 CPU 22.7%，其他程序保持运行。
采用交错分组降低漂移影响，不能消除共享主机噪声。Windows 粗粒度 CPU 计数对
亚毫秒请求不可靠，不用其解释小请求差异。全程进程峰值工作集分别约 25.9、29.7、
33.6 MiB；它们包含此前场景的分配，不能当作每次查询的内存用量。

[I] 批量场景主要受客户端解码和对象构造成本影响：独立 cProfile 中 Python BSON
递归解析/数组/字符串占主要调用时间；解码组件已接近原生 Python 整次查询耗时。
回放服务端每次批量处理约 0.8 ms，低于客户端 12–30 ms，当前证据不支持网络
带宽为主要瓶颈。小请求的解码仅约 15–27 微秒，调度和本地 RPC 占比更大。
剖析未用于上表计时，不把 profiler 放大后的时间当作真实延迟。

[I] 对 agent，先复用常驻进程和连接、批量读取，最有实际价值；本次新进程小查询
与常驻小查询差数十至数百倍，但两者包含的工作不同，不能称为同一请求的优化倍数。
Rust 批量路径值得继续优化；是否采纳还需真实 MiniQMT/大 QMT 服务上的同条件
延迟、字段语义、订阅、长时间心跳及断线验收。账户四项快照、历史和集合竞价
不在本轮性能结论内。
